# Architecture

```
formMCP/
├── core/            formmcp-core: the family list (core/data/family.json, compiled in), reach, child servers, the MCP server
├── cli/             formmcp-cli: apps, app, reach, mcp, version
├── src-tauri/       the shell: the window, and `formmcp mcp` with no window
├── frontend/        the window: tokens, layers, one list
├── setup/family.py  core/data/family.json from formcompiler's registry
└── assets/          the owner's icon
```

## One engine, two thin surfaces

`formmcp-core` owns everything that matters: reading the family list and answering MCP over stdio and, from v0.5.0, Streamable HTTP (`http.rs`: a hand-rolled HTTP/1.1 listener on 127.0.0.1, one request per connection, one shared `Gateway` behind a lock, sessions mapped to the agent they count as). `formmcp-cli` and the shell call it and add nothing. The installed app's own binary serves MCP when its first argument is `mcp`, before any window code runs, so an installed copy is its own launcher.

## The gateway (v0.2.0)

`reach.rs` decides, without starting anything, how each app's server can be started: a checkout's own launcher under `FORMMCP_DEV_ROOTS`, or `app-mcp` through FormPortal for an app in FormPortal's `installed.json`. `child.rs` runs one app's server as a child process over stdio: initialize, tools/list (all pages), calls with deadlines, requests from the app refused so nothing waits, the last stderr lines kept for error messages, and the process ended when formMCP ends. `mcp.rs` holds a `Gateway` (the list, the places, the running servers by app id, the settings read again on every request, and the agent the session counts as) behind eight tools; formMCP's own tool list never grows with the apps. `child.rs` keeps each app's declared capabilities, so resources and prompts are asked for only when the app offers them, and pages through any list. `toolcache.rs` keeps the names of each started app's tools in `tools/<id>.json`, for the window's per-tool switches.

## Catalogue, suggestions, exposure and clients (v0.3.0)

`catalog.rs` reads the signed family catalogue (or FormPortal's kept copy) once per session and lays it over the built-in list, with FormPortal's trust model and keys. `suggest.rs` scores a task's words against each app's name, kind, summary and a per-kind word list and adds the next step. `settings.rs` holds the apps whose tools are always shown; `mcp.rs` adds them to `tools/list` under `<id>__<tool>` and routes their calls. `clients.rs` (from FormPortal's `agents.rs`) writes and removes formMCP's entry in Claude Code, Codex and Cursor.

## Safety and tracing (v0.7.0)

Before `child.rs` starts a FormPortal install, `verify.rs` reads FormPortal's `installed.json`, refuses a record whose folder is outside FormPortal's `apps/<id>` folder, and hashes every file in the install (SHA-256; symlinks by their target). The first start of a version (same version, FormPortal digest and path) records the result in `verified.json`; later starts compare and refuse with the new, changed and gone files named. From v0.7.1, when FormPortal's record names a files record (`files`, FormPortal 0.46.0 and later: every installed file's SHA-256, written at install), formMCP compares with that instead, so nothing depends on formMCP's first start, and a record for another app or version refuses. Without one (older FormPortal), the first start is the reference and `verify --trust` records again; `--trust` does not override FormPortal's record. Checkouts are not checked. `secrets.rs` keeps each secret in the system keychain (service `formMCP`, account `<app>/<NAME>`, through the keyring crate: Keychain on macOS, Credential Manager on Windows, the Secret Service over D-Bus on Linux), lists only names in settings.json, refuses names that change how programs run (PATH, LD_ and DYLD_ prefixes and others), and passes the values to the app's server as environment variables. `redact.rs` replaces the known secret values (and the HTTP token) and token shapes in every string of an answer, leaving base64 `data` and `blob` fields alone; `log.rs` always passes events through it. `hooks.rs` runs the before command with the call as JSON on stdin (arguments cleaned, long strings shortened): exit 0 with nothing or `{"decision":"allow"}` allows, `{"decision":"deny","reason":...}` or exit 2 refuses, anything else (not found, other exit, not JSON, past `FORMMCP_HOOK_TIMEOUT`, 10 s) refuses. The after command gets the outcome and cleaned result in the background. `telemetry.rs` posts one span and two delta metrics (`formmcp.operations`, `formmcp.duration` in ms) per call and app start as OTLP JSON to `<address>/v1/traces` and `/v1/metrics`, with `OTEL_EXPORTER_OTLP_HEADERS`; the stdio server waits up to 5 s for sends in flight before it exits.

## The family list

`core/data/family.json` (format `formmcp-family`, version 1) is generated by `setup/family.py` from formcompiler's registry: each app's catalogue id, name, kind and summary, its repository, its release state, whether it is released at all, and its `agents` block (`mcp`, `skills`, added in formcompiler 0.4.0). It records formcompiler's version and commit. It is compiled into the engine with `include_str!` and imported by the window at build time, so both read the same bytes and nothing is fetched.

Later versions read the signed family catalogue (`apps.json`) when it can be reached and keep this file as the offline fallback.

## The window

From v0.6.0 the gateway sweeps idle on-demand apps at every request (`sweep_idle`) and, at initialize, starts the session's `session` apps on background threads (`start_early`), whose results `server()` takes when the app is first asked for; `settings.rs` resolves the agent's profile into what is off and each app's policy. The shell adds `set_start` and the `profile_*` commands. From v0.5.0 the shell also answers `set_for`, `tool_list`, `tool_load` (starts the app once, in the shell, to learn its tools), `set_tool`, and `http_switch`, `http_token` and `http_rotate`; it holds the HTTP server while the window is open, and `snapshot` adds each app's agents and off tools and the HTTP state. From v0.4.0 the shell answers four commands: `snapshot` (the family over the catalogue, each app's install state, route and switch, the three clients' states), `set_expose`, `connect` (one client, with this program as the launcher) and `log_tail`. Because each client starts its own formMCP server, the window learns what agents do from `log.jsonl` in formMCP's settings folder, which every server appends to: sessions, tool calls (names, app, outcome, time) and app starts. Arguments and results are never written.

The page is built once from the same list. The body stays hidden (`html.booting`) until `main.ts` has created every row and filled the counts, then the class is removed: the first frame is the final layout, on the theme's ground colour, with no flash. The filter chips toggle `hidden` on the existing rows and rewrite one count line; nothing is rebuilt. Every `z-index` comes from `layers.css` and every colour, space and radius from `tokens.css` (the Form family tokens, with formMCP's orange and violet accents).
